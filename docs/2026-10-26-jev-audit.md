# JEV audit of the product flow (2026-10-26)

Question: can the calibrated JEV model rank the product's improvement levers for speed, cache economy, quality and codegen?

Method: four `jev-classify` calls to the TypeSafe backend (`jev-latest`, ~0.4-0.65 s each). Each call carried the same compact brief with the measured numbers (router 7/10 at 0.28-0.34 s, JEV 8/10 at 404 ms, flow 0.64 vs 1.73 s, programming flow 0.091/2.897/0.570 s, infer 0.79 s, map 0.29-0.37 s, context 0.26 s / 28.6 KB vs 1.19 MB raw, edit 0.31-0.39 s, codegen 0.01-0.17 s, daemon handlers inline, no Windows daemon, 27 flaky tests, auth lockout, explore without tools) and 2-3 questions with explicit choices.

## Results

| axis | question | answer | p |
|---|---|---|---|
| speed | biggest lever | startup | 0.49 |
| speed | skip plan by default | no | 0.70 |
| speed | is a resident CPU-executor daemon worth it | yes | 0.45 |
| economy | map worth it for one file | only multi-file | 0.42 |
| economy | best cache strategy | smaller context | 0.74 |
| economy | **target context size** | **28 KB** | **1.00** |
| quality | biggest quality risk | auth lockout | 0.47 |
| quality | should tests gate every merge | only affected | 0.52 |
| codegen | how to make it near-instant | cache the inferred contract | 0.57 |
| codegen | **codegen mandatory in every programming flow** | **no** | **0.93** |

## What is actionable

Only two answers clear the 0.8 cutoff the same model recommended in the previous consultation:

1. **Keep the context packet at 28 KB** (p 1.00). This contradicts the earlier framing of the 13.7 KB -> 28.6 KB change as a regression. With the measured comparison (28.6 KB vs 1.19 MB reading the matched files, 42x smaller), the larger packet is the right trade; do not shrink it to 14 KB.
2. **Codegen should not be mandatory in every programming flow** (p 0.93). This conflicts with the owner's instruction that codegen is mandatory. Recorded as a disagreement, not applied: the owner owns that rule. The measured cost of forcing it is the 0.79 s `codegen infer` on projects without a contract.

## Where the audit is not usable

- Seven of ten answers sit at 0.42-0.70, i.e. a coin flip to a weak lean. They are not a roadmap.
- The economy axis contradicts itself: "smaller context" (0.74) and "28 KB target" (1.00) in the same call. Treat that axis as unreliable.
- The model has no access to the runtime internals, so "biggest lever" (0.49) is a guess dressed as a choice.

## Conclusion

JEV is a good **classifier** (8/10 on labelled tasks, fixes all three router errors) and a weak **architecture advisor** (coin flips on levers, contradictory on cache). Use it as the router's confidence-gated fallback, not as the source of the roadmap. The roadmap stays with the measured numbers:

1. Wire the JEV fallback at the 0.8 cutoff.
2. Move the daemon's four CPU-bound handlers onto the CPU executor (measured: daemon vs cold TIE at 159 vs 183 ms; cold context 10.6-12.1 s).
3. Expose MCP to `explore` subagents (the only route today is `general`).
4. Keep two calls for a known-file edit (0.64 s) and infer-in-background for a project without a contract (0.56 s vs 1.50 s).
5. Keep the 28 KB context packet (JEV-confident and measured 42x smaller than raw).

## Reproduce

```bash
SIMPLICIO_JEV_BACKEND=typesafe simplicio-jev jev-classify --simplicio-plugin-request < brief.json
```

Backend: `typesafe` persisted in `~/.simplicio/jev.json`; key at `~/.config/typesafe/api_key` (0600, never in the repo).
